1. 系统概述

系统由浏览器界面、学习业务服务、独立认证服务、本地存储和外部模型服务构成。支持资料阅读、带引用问答、章节学习、练习反馈、错题复习、学习档案与管理员账号操作。



2. 设计约束

主要设计约束如下。

范围：课程作业与本机演示优先，不以生产级多租户服务作为已实现目标。

协议：浏览器与业务服务通过 HTTP/JSON 与 SSE 交互；认证通过独立 HTTP 接口，真实模型走外部 HTTPS API。

环境：Python 3.10+、SQLite 和可写文件目录；前端原生 JS，无构建依赖；Windows 启动器与本机文件打开属于平台相关部分。

接口：认证服务默认 127.0.0.1:8740，业务默认 127.0.0.1:8737；服务地址可配置，端口不可与旧副本混用。

界面：沿用 main merged 的首页、欢迎页、SVG 资源及个人信息交互，在同一布局下增加功能。

质量：拒绝未授权核心资料操作，待审核资料不参与检索；缓存须随索引版本、配置及用户上下文失效。

依赖：用户具备资料使用权限并自行提供 Key。外部服务可能限流、断连或返回不可靠内容；PDF 文字提取不包含 OCR。



3. 设计策略

采用浏览器表现层、业务编排层、领域与存储模块的职责分离。

扩展：资料解析集中于 extras/pdftext，检索集中于 rag，模型接入集中于 deepseek；新功能通过 server 路由和对应前端模块接入。

复用：对话、章节辅导和复习共用模型客户端；资料切片及检索结果共用于引用生成；工具调用复用存储及权限规则。

折衷：标准库与 SQLite 降低安装成本，BM25 不依赖向量服务；代价是语义召回和高并发能力有限，需用真实课程问题评估。





4. 系统总体结构

物理部署：浏览器 → 本机业务进程 8737 → 本机用户数据库/文件；业务进程 → 认证进程 8740 → auth.db；业务进程 → 外部模型 HTTPS API。

逻辑结构：界面 → HTTP/SSE 路由 → 账号校验与用户目录绑定 → 资料/学习/模型模块 → SQLite 与文件。认证库独立于学习库，避免混合密码和学习内容。

拆分理由：认证可独立配置，学习数据留在本机；检索、解析与模型模块可分别测试；前端只通过受控接口访问数据。

协作流程：登录获得会话并绑定用户目录；导入资料保存正文及源文件、切片并递增索引版本；提问检索证据后组装提示，流式生成并检查引用，最后保存会话。



5. 子系统N的结构与功能

子系统按职责划分如下。

表现子系统：app.js 负责路由和资料/学习交互，auth.js 负责账号，extras.js 负责扩展看板，agent.js 负责工具流，landing.js/ui.js/keepalive.js 负责欢迎页、偏好和存活心跳。

业务子系统：server.py 编排 HTTP/SSE；store.py 管理用户数据；rag.py 完成切片检索；deepseek.py 与 prompts.py 封装生成；tools.py 封装工具；extras.py/pdftext.py 提供扩展和文件解析。

认证子系统：AuthClient 维护登录与刷新，AuthStore 校验密码和角色、保存会话；业务服务再次执行资源权限。学生禁止核心资料写入，管理员账号管理仍须认证服务授权。
