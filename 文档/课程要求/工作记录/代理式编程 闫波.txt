===== 第 10 页 =====

大模型与执行能力
仅具备对话能力并不足够 ，关键在于能够真正
完成任务。能力落地主要包括以下几条路径：
• 提示工程 （Prompt）：通过更优质的指令
引导模型输出。
• 检索增强（RAG）：使模型能够调用外部知
识和最新资料。
• 工具调用（Function Calling）：让模型具
备调用API、查询数据库和执行代码的能力。
• 插件与生态 ：将模型能力接入真实世界的业
务系统。
当模型能自己决定调用什么工具、并根据结果
继续行动时，就出现了智能体（Agent）。

===== 第 18 页 =====
18
代理式编程的分类依据
代理式编程出现后，很快从单一形态走向多元分化。不同产品之间的差异，不再只是模型能力或代
码补全效果的差异，而更多体现在用户从哪里进入，以及如何与 Agent 协作。因此，理解代理式
编程工具，不能只看背后的模型和厂商，更要看它所处的使用场景、交互方式和协作边界。
课程采用的分类依据：按使用入口 / 交互形态分类，而非按厂商或模型。
原因是对于开发者而言，工具使用的场景与方式，比其背后采用哪一家模型，更影响
开发体验。
提示：同一厂商可能覆盖多个类别（例如 Claude Code 同时出现在多种分
类中）。因此，分类依据的是产品形态，而非厂商归属。

21

• 特点： Agent 是产品的原生功能 ，与编

化 diff、即时预览、补全与对话一体；上

• 擅长任务：日常功能开发 、需频繁人工审

习惯图形化 IDE 的开发者。
第一类是把 Agent 做进命令行，第二类是把编
辑器重做成 Agent 优先，是当下的主流形态。


===== 第 22 页 =====
22
以插件形态存在的智能助手
• 特点：起步于自动补全 /对话辅助，以辅助
人为主、人始终主导；近年加入 Agent 模
式，但自主程度常弱于类型一和类型二。
• 优势： 无缝嵌入既有工具链 、生态成熟 、
企业接受度高。
• 擅长任务： 不改变现有环境下提效 ，如补
全、解释、生成测试、渐进式引入 AI。
属于不完全 agentic，生成建议、并局部修改代码，但默认不会自己跑一系列任务。常见
于团队平滑过渡到 AI 编程的起点，且正快速进化出 Agent 能力，边界在模糊。
