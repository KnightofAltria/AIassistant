# 额外交付材料与提交检查表

课程结束要求不等于九份模板文件。依据《卓越工程综合训练-2026课程安排》第 19–22、24、27–37 页，还应准备问题陈述、周报、源代码、手册、项目总结、评分及讲评材料。本文件给出写法和可填写框架，后续请用真实项目内容替换。

## 一 额外材料如何写

### 1 用户需求及问题陈述

用户需求可能来自教师提供的项目案例或真实访谈。本文件夹未包含课件提到的用户需求样式和问题陈述附件，也没有指定项目案例，因此先采用下面的简版结构。

| 内容 | 填写方法 |
|---|---|
| 需求来源 | 需方、访谈日期、已有资料、待确认事项，附真实记录 |
| 当前问题 | 谁在什么场景遇到什么困难，现有办法为什么不够 |
| 项目目标 | 完成哪些业务，怎样操作，需要什么性能与限制 |
| 业务边界 | 首版包含和排除什么，依赖哪些外部系统 |
| 成功条件 | 用几条可演示、可测试的验收场景说明 |
| 确认记录 | 需方意见、修订和确认日期；没有确认时保留待确认 |

设备预约示例：拟为实验室学生和管理员提供设备查询、固定时段预约、审批、领用和归还管理，解决预约信息分散及借还状态难以追踪的问题。首版通过浏览器访问，采用本地测试账号；同设备同一时段不允许重复占用，用户可查看本人申请，管理员可审批并记录借还。该段是选题描述示例，不能当作已完成调研的结论。

### 2 项目进展周报

课程要求按周提交，并记录个人贡献。每周安排课外小组例会，结合每周至少两次教师指导更新计划；谁负责发送周报应提前明确。

可直接使用的周报结构：

| 字段 | 待填写内容 |
|---|---|
| 基本信息 | 项目、周次、实际起止日期、当前软件与文档版本 |
| 本周目标 | 本周原计划完成的需求及任务编号 |
| 实际成果 | 已完成事项、负责人、代码提交或文件位置、演示或测试证据 |
| 计划偏差 | 未完成任务、原因、影响、补救措施和新日期 |
| 下周计划 | 任务、负责人、依赖、预计人时、验收条件 |
| 风险与待决事项 | 需要教师或组内解决的问题、责任人及期望解决日期 |
| 会议及变更 | 讨论结论、需求变化、关联记录 |
| 个人投入 | A、B、C 的真实工时与具体成果，不以代码行数直接代替贡献 |

好的写法是“完成 FR-RES-01 接口，关联提交及测试 TC-RES-001；并发冲突仍在处理中”。“开发完成 80%”若无明确分母，无法帮助判断进度。

### 3 用户手册

面向学生和管理员写，不以开发框架为主线。建议结构：产品用途与适用版本 → 账号和角色 → 学生预约流程 → 管理员审批 → 领用归还 → 取消及异常处理 → 查询统计 → 常见问题与帮助。

每个操作包含：目标、前置条件、操作步骤、实际界面截图、成功结果、常见失败原因。至少完整写一条借还流程和一条取消重订流程。截图来自最终候选版本；演示账号使用专门的测试账号。

验证方法：请没有编写该章节的组员照手册操作，记录无法理解或无法完成的步骤，再修改。

### 4 安装手册

建议结构：运行环境及版本 → 交付包说明 → 配置项 → 数据库初始化或迁移 → 启动步骤 → 首次登录和演示数据 → 健康检查 → 停止和重启 → 备份与恢复 → 常见错误 → 卸载及数据保留。

每条命令或操作要说明执行目录、必要参数、期望结果。配置文件提供示例，真实密钥不放入源码包。数据库必须有初始化方式，不能只交某人的本机数据库。

写清部署方式是本地、局域网还是远程服务器；没有验证的操作系统不能列为“已支持”。由另一名组员在不同电脑或干净环境按手册重现，并保存版本、时间及结果。

### 5 项目总结报告

建议结构：项目目标与最终范围 → 计划与实际对比 → 已实现和未实现功能 → 架构及关键技术结果 → 测试与质量 → 分工及贡献证据 → 主要变更 → 问题与经验 → 后续改进。

用证据说明结论。例如比较“原计划第 3 周实现并发控制、实际第 4 周完成，导致统计页后移”的原因和改进。区分未实现、实现未测、验证通过，不能把计划中的功能全部列为成果。

### 6 源代码与可运行交付包

源代码清单建议包括：项目目录说明、主要模块与负责人、启动入口、构建运行步骤、依赖锁定文件、数据库迁移与测试数据、测试脚本、配置示例、交付版本或提交标识。若引用第三方代码或资源，保留来源和许可说明。

交付前实际从交付包安装运行一次。不要依赖只有开发电脑上存在的绝对路径、未交付数据或账号。

### 7 中期汇报

课程要求展示需求分析、系统设计、项目进展、后续安排及问题。可按 7 个部分准备：用户及痛点、范围与验收目标、用例和领域模型、架构及数据设计、已运行流程、三人分工和进度、风险及后续计划。

中期日期由教师确定，本方案建议在项目第 4 周具备可汇报状态。尚未完成的页面要标为原型，不以静态截图代替已运行成果。

### 8 最终项目讲评和个人答辩

组长先讲项目整体目标、过程及结果，再由三人说明各自模块。个人讲述控制在课件给出的 10 分钟以内，并预留约 5 分钟提问。

个人 10 分钟示例：1 分钟说明职责与需求；2 分钟演示核心流程；3 分钟解释状态、数据和关键设计；2 分钟说明测试与一个真实缺陷的修复；2 分钟说明贡献证据、取舍和总结。

每个人准备回答：为什么这样设计、哪条规则最难、如何验证、与其他模块如何衔接、如果增加需求要改哪些地方。演示使用固定测试数据，并预备本地可运行版本与录屏作为故障备用。

### 9 小组评分

第 37 页要求按课程群提供的模板，由组长根据表现单独评分，不与组员商量，直接提交指导教师，电子版即可。文件夹没有该评分模板，因此不能据此虚构评分表字段或人员得分。

你们可以日常记录任务、评审、测试和沟通贡献；最终评分仍由组长按实际表现和教师模板填写。

## 二 建议的统一文档追踪记录

| 需求 ID | 需求条目及版本 | 设计章节 | 页面或模块 | 代码位置或提交 | 测试用例 | 测试结果与证据 |
|---|---|---|---|---|---|---|
| FR-RES-01 | 提交预约，待确认基线 | 预约模块与数据库占用设计 | UI-RES-01、预约模块 | 开发后填写 | TC-RES-001 至 006 | 未执行 |
| FR-LOAN-01 | 领用归还，待细化 | 借还模块、loans 表 | UI-LOAN-01 | 开发后填写 | 设计后填写 | 未执行 |

这张表是贯通文档、代码和证据的建议附件，不是课件要求的额外独立报告。也可以直接放入需求说明或测试报告。

## 三 交付目录建议

以下是未来项目交付包结构建议，不表示这些文件已经生成。

```text
项目交付包/
  00_交付说明及版本清单/
  01_问题陈述与需求来源/
  02_项目计划/
  03_需求规格说明书/
  04_设计文档/
    体系结构设计报告
    用户界面设计
    数据库设计报告
    模块设计报告
  05_测试资料/
    系统测试计划
    测试用例与执行记录
    测试报告及证据
  06_用户手册与安装手册/
  07_周报与项目总结/
  08_源代码及运行资料/
  09_讲评材料/
```

小组评分由组长单独提交，按课程要求处理。第 37 页允许根据指导教师要求把概要及详细设计合成一份；在未确定前，按四份现有设计模板组织内容即可。

## 四 提交前逐项检查

### 课程内容

- [ ] 选题符合指导教师给定案例或已确认的自主选题范围。
- [ ] 问题陈述明确，需求来源和确认过程真实。
- [ ] 九份模板对应内容齐全，裁剪项有理由，设计合并形式符合教师要求。
- [ ] 用户手册、安装手册、项目总结和周报齐全。
- [ ] 源代码、依赖、数据库初始化和运行说明完整。
- [ ] 中期与最终讲评材料、个人成果说明已准备。
- [ ] 组长已取得课程群的评分模板并按要求单独提交。

### 内容一致性

- [ ] 项目名、角色、模块、字段、状态、接口和编号前后一致。
- [ ] 每个必做需求都有设计和测试，未实现项已明确标记。
- [ ] 图、截图、源代码和文档对应同一个交付版本。
- [ ] 目录重新生成，页码、标题、表格和图注正确。
- [ ] 删除旧模板提示、无关机构名称和默认勾选结果。
- [ ] 成员姓名、日期、评审结论及签名均真实。

### 可运行和质量

- [ ] 从交付包在另一环境重现过安装及完整业务流程。
- [ ] 并发冲突、重复请求、越权、非法状态等关键用例已测试。
- [ ] 测试报告写明环境、版本、执行时间及真实统计口径。
- [ ] 严重缺陷已关闭或明确阻碍交付；普通遗留缺陷有说明。
- [ ] 演示数据可复位，演示账号不使用真实个人密码。
- [ ] 每位组员都能解释自己的设计与测试，贡献可以追踪。

### 提交形式

课件第 37 页要求：纸质版打印并装入档案袋，袋面注明班级、小组和成员；源代码清单、讲评 PPT、小组评分不要求纸质版；电子版通过 U 盘拷贝给指导教师，无需刻录光盘；评分由组长单独发教师。若教师后续发布新的要求，以其通知为准。

- [ ] 已确认最终提交日期、讲评日期及收件方式。
- [ ] 已核对纸质和电子版内容一致。
- [ ] 已检查 U 盘中的文件可打开、源码包可解压、版本标识正确。

## 五 使用代理式编程时如何留存工程证据

《代理式编程 闫波》第 62–71 页强调清晰需求、先规划、小步实现、测试和人工评审。可以将这些方法用于项目全过程，而不必开发一个 AI 产品。

每次辅助开发留下简要记录：需求编号、输入约束、采用的方案、人工修改原因、测试结果及对应提交。组员需要理解并复核业务逻辑，尤其权限、状态和数据一致性。项目总结可据真实记录说明辅助工具用在何处，以及人如何发现和修正问题；不要把工具生成量直接当作个人能力或项目质量。
